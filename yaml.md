Yes, Mainbrella should publish its YAML format openly. But I wouldn't try to establish it as a new industry standard yet.

I think there's a genuine opportunity here, particularly because Mainbrella is designed for AI agents as well as human developers.

The distinction I'd make:

- Publish a specification now: Document the format, version it, provide a schema, and let other tools generate and consume it.
- Pursue a standard later: Once other projects actually use it, consider making it vendor-neutral and establishing independent governance.

The strongest positioning isn't "a better Dockerfile." It's a portable recipe for an AI agent to prepare, launch, and preview a GitHub repository.

## What's already out there?

| Format              | Primary purpose                                                          | Overlap with Mainbrella                   |
| ------------------- | ------------------------------------------------------------------------ | ----------------------------------------- |
| `Dockerfile`        | Build container images                                                   | Environment and dependencies              |
| `compose.yaml`      | Run applications with multiple services                                  | Startup, ports, networks, databases       |
| `devcontainer.json` | Reproducible developer environments                                      | Setup commands, tooling, forwarded ports  |
| Devfile             | Describe cloud development workspaces                                    | Development lifecycle and execution       |
| Railway IaC         | Define platform services and deployments                                 | Deployment configuration                  |
| Mainbrella YAML     | Launch a repository into an interactive machine with an optional preview | A simpler, agent-friendly launch contract |

The [Dev Container specification](https://containers.dev) already covers much of the setup lifecycle, and [Docker Compose](https://docs.docker.com/reference/compose-file/) covers multi-service runtime definitions.&#x20;

So the opportunity isn't to duplicate those formats. It's to complement them.

## What I would publish

Call it the Mainbrella Launch Manifest, initially version 0.1.

Keep the existing fields and publish a JSON Schema, examples, validator, and a small open-source parser. YAML and JSON should represent the same underlying data.

But I'd distinguish two use cases:

1\. A launch request generated by an agent. This is what you have today: a GitHub repository, immutable commit, runtime, setup script, start script, and port. It belongs outside the repository because it's generated for a particular launch.

2\. A launch manifest maintained by a repository owner. This should live inside the repository. It shouldn't need to repeat the repository URL or commit. It should be able to reference a Dockerfile, Compose service, or Dev Container definition instead of duplicating their instructions.

For example, a future manifest might look like:

```
schemaVersion: 1

build:
  dockerfile: Dockerfile
  target: relay-server-local-source

run:
  port: 3005
  healthcheck: /
```

This is a proposed format, not YAML the current Mainbrella `/run/` parser supports.

I would make the manifest an optional override, not something every GitHub project needs to adopt.

## The competitive advantage isn't the YAML

It's the ability to say:

> Mainbrella can understand how your project runs, whether its instructions are in a Dockerfile, Compose file, Dev Container, or a simple launch manifest.

There's already a particularly relevant precedent: [Devfile](https://devfile.io/), an open specification for containerized development environments that supports commands, project sources, and endpoints.&#x20;

More importantly, a new standard needs multiple implementations. A YAML format supported only by Mainbrella is a useful product configuration, but not yet an industry standard.

My suggested milestone would be to get a second independent runner to consume the same manifest successfully, perhaps a local Docker or OrbStack implementation. Then you'd have evidence of genuine portability.

## One thing I would prioritize first

Make Mainbrella automatically select among existing project definitions, preferring a supported Docker/Compose build where appropriate and falling back to agent-generated instructions when necessary.

Right now, the Happier experience demonstrates the problem: the AI reconstructed a large build process that was already documented in the repository, and the reconstructed process introduced its own installation problems.

The real product win is eliminating the need to generate that YAML at all for most repositories.

Publish the existing format openly, certainly. But invest your engineering effort in making Mainbrella understand established formats rather than convincing developers to maintain another one.
